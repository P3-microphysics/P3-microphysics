# Test Summary – v5.6.4 (automated, parallel generation of the lookup tables)

**Date:** 2026-10-23
**Change:** branch `dev-lut` (from `dev` at v5.6.3), merged into `dev` as v5.6.4. The lookup-table generators
(`src/create_p3_lookupTable_1.f90`, `_2.f90`, `_3.f90`) take their outer-loop indices as command-line arguments,
and a new driver, `src/make_luts.sh`, runs them in parallel and assembles and checks the tables.
`src/microphy_p3.f90` changes only in its version markers and one comment (§9). Added on 2026-10-24, before
v5.6.4 was distributed: the procedures shared by the generators moved into one module (§9).
**Prepared by:** Jason Milbrandt, with Claude Code
**Scope:** regeneration of all four lookup tables with the new code, compared with the shipped tables and with
the previous (manual) procedure run with the same compiler; kin1d with the regenerated tables; review of the
code changes. No host-model run: the scheme and the tables are unchanged.

---

## Summary

Until v5.6.3 the tables were generated by hand: each generator was cut into two files at a marker, the outer-loop
indices were inserted into the source and one executable was compiled per index combination (55 for the 3-moment
LT1), the outputs were concatenated in directory-listing order, and LT2 was compiled and run four times for the
liquid-fraction combinations `(Fl1,Fl2)`, with its columns pasted together by hand. As committed, the generators
could not produce the shipped files without further edits: LT2's outer loop was active while its output file name
used the loop index before the loop; LT3 had no parallel procedure and its outer loops were commented out; LT2 and
LT3 wrote header versions (`6.2_00`, `1.4-3momI`) that `p3_init` rejects, so the shipped headers were edited by
hand.

v5.6.4:
- Each generator computes one **block** per run, given on the command line: LT1 `3 i_Znorm i_rhor i_Fr` (3momI,
  220 blocks) or `2 i_rhor i_Fr` (2momI, 20 blocks); LT2 `Fl1 Fl2 i1` (100 blocks); LT3 `i_Znorm i_rhor`
  (400 blocks). `log_3momI` (LT1) and `Fl1`, `Fl2` (LT2) are read at run time; no source is edited and each
  generator is compiled once. Every LT2 run writes the 6 index columns.
- The generators write the headers `p3_init` expects, with an empty second line whatever the compiler.
- Each generator stops unless default `real` and `double precision` are both 8 bytes. The previously documented
  gfortran flag `-fdefault-real-8` alone makes `double precision` 16 bytes, so `compute_mu_3moment` ran partly
  in quad precision in such builds.
- `src/make_luts.sh TABLE [-j N]` (`TABLE` = `lt1-2mom`, `lt1-3mom`, `lt2`, `lt3`, `all`) compiles each generator
  once with double-precision, value-safe flags (ifx/ifort `-r8 -O2 -fp-model precise`; gfortran
  `-fdefault-real-8 -fdefault-double-8 -O2 -ffp-contract=off`), runs the blocks N at a time, checks that every
  block succeeded and all blocks of a table hold the same rows, assembles the blocks in index order (LT2: the four
  runs' index columns checked row by row, data columns joined in the order `p3_init` reads), checks the header
  and the row counts against the table's axes, and writes the table with a provenance file (`.info`).

**Result: PASS.** The regenerated tables reproduce the shipped tables (LT1-2momI and LT3 byte-identical; LT2 and
LT1-3momI identical in every value), and kin1d with the regenerated tables is bit-identical to kin1d with the
shipped tables. All four tables are made in 40 minutes on 128 cores.

`-r8 -O2 -fp-model precise`. Compared byte by byte, and token by token with a comparison script (header, row and
column counts, index columns, every value as printed and as a number, whitespace ignored).

| Table | Rows | Result |
|---|---|---|
| `p3_lookupTable_1.dat-v6.9-2momI` | 124,000 | **byte-identical** |
| `p3_lookupTable_1.dat-v6.9-3momI` | 1,364,000 | 5,324,000 values identical except **79 signed zeros** in column 32 (`m6shd`): `-0.00000E+00` in the shipped file, `0.00000E+00` now. Numerically equal; `p3_init` reads both as 0. |
| `p3_lookupTable_2.dat-v6.2` | 250,000 | all 2,000,000 values identical; the shipped file is tab-separated with a hand-edited header, the new one fixed-width (`6i5,8e15.6`), read identically by `p3_init` |

## 2. Against the previous procedure, same compiler and flags

The committed generators of v5.6.3 were run by the previous manual procedure, reproduced by a script (outer
indices inserted into the source, one executable per block; LT3, which had no parallel procedure, run serially),
with the same compiler and flags as §1.

| Table | New code vs previous procedure | Previous procedure vs shipped |
|---|---|---|
| LT1-2momI | identical in every value | data rows byte-identical; header line 2 differs (ifx writes a space for an empty list-directed record) |
| LT1-3momI | **identical in every value** (5,324,000) | the same 79 signed zeros as §1 |
| LT2 | identical in every value | identical in every value |
| LT3 | identical in every value (the header now as `p3_init` expects) | data rows byte-identical; header as written by the old code (`1.4-3momI`) |

So the new code reproduces the previous procedure exactly, and the 79 signed zeros come from the build that made
the shipped LT1-3momI (another compiler or flags; the shipped files' empty header line 2 also points to a different
compiler), not from this change.

**Floating-point model.** With the flags of the old instructions (`ifx -r8`, i.e. the compiler's default
floating-point model, which allows reordering), the previous procedure gives an LT1-2momI that differs from the
shipped table in 13 values (column 7, up to 9e-4 relative, at values ~1e-14); LT3 is unaffected. With
`-fp-model precise` the shipped LT1-2momI is reproduced byte for byte. The driver uses value-safe flags for this
reason.

## 5. Review of the changes

Two independent reviews of the code changes (AI-assisted, read-only, given the code but not the expected
answer):
- Generators: no change can alter a written value. `log_3momI`, `Fl1`, `Fl2` changed from compile-time constants
  to run-time variables: `log_3momI` appears only in conditions; every use of `Fl1`/`Fl2` has the form
  `(1-Fl)*X + Fl*Y`, which is exact for Fl = 0 or 1. Header writes, file names, loop bounds and the 2momI value
  `i_Znorm = -9` match the previous behaviour. One latent issue predating this change was made explicit: LT3's
  `zqerror` is read by its convergence test before it is first set; it is now set to 0 at program start (its
  previous value from static storage), and the table is unchanged.
- Driver: tested with a stand-in generator in each of these cases, every one of which ends without writing a
  table: a block exiting non-zero, a killed block, a missing block file, a block cut short but exiting 0 (in
  LT2's (0,0) and (1,1) runs, and in LT3), an LT2 row of the wrong length, a failed run over an earlier table, two
  runs on one output directory, the driver itself being terminated. Results identical for `-j 1` and `-j 8`.
  The issues found in the first review were fixed before the verification runs of §1 (row-length check, removal
  of an older table, output-directory lock, per-block row check, termination of running blocks).

## 6. Cost

One core per block (ECCC HPC, ifx), measured: LT1-3momI 220 blocks of ~30 min (~115 core-hours), LT1-2momI 20 of
~15 min, LT2 100 of ~7.5 min, LT3 400 of ~15 s; `all` ~135 core-hours, **40 minutes on 128 cores**. Previously
the run time was bounded by the 55 LT1-3momI blocks of ~2.1 h each (by i_Znorm and i_rhor only), and a serial LT3
took 1.6 h.

## 7. Not tested

- gfortran (e.g. on macOS) with the driver. Not expected to be bit-identical with ifx (different math libraries);
  nearly all printed values should agree.
- Host models: not needed, since the scheme and the table values are unchanged.

## 9. Addendum (2026-10-24): shared procedures in one module; a comment in `microphy_p3.f90`

**Change.** The procedures that the generators carried in two or three copies are now in one module,
`src/p3_lookupTable_common.f90` (`module p3_lookupTable_common`), which each generator uses:

| Procedure | Copies before | Note |
|---|---|---|
| `gammq` (with `gser`, `gcf`, now private to the module) | LT1, LT2, LT3 | identical code; a misspelled declaration (`gammser` for `gamser`, implicitly typed) corrected |
| `intgrl_section_Fl` (5 partial integrals) | LT1, LT3, and LT2 under the name `intgrl_section` | identical code; LT2 now calls it by this name |
| `intgrl_section` (4 partial integrals) | LT1 | used by LT1 only, kept beside its 5-integral form |
| `diagnostic_mui` | LT1, LT2 | identical code, two signatures; LT2 now uses LT1's, passing `mu_i_min = 0`, `mu_i_max = 20` (its previous constants) |

Calls are now checked against explicit interfaces. Removed as never called: `compute_mu_3moment` and
`compute_mu_3moment2` (LT1), `compute_mu_3moment` and `compute_mu_3moment_2` (LT3), and LT3's declarations of
functions it did not define. The generators are compiled with the module first (`make_luts.sh` does this; the
generators' header comments give the commands).

In `src/microphy_p3.f90` the comment above the `dnu` table (droplet spectral shape for the Seifert and Beheng
(2001) scheme) now states how the table was derived. No code changes.
